# Feature brief: Flexible selective VPN routing

_Generated by `feature-interview` on 2026-09-12. Review and update before implementing._

## Goal

Design a simple, secure, and flexible way to introduce the existing NordVPN subscription into the home-server stack without routing all server traffic through the VPN. The immediate goal is to resolve Home Assistant's Home Connect connectivity issue while preserving normal LAN access and keeping the design extensible for future service- or destination-specific routing.

## Scope

- **Product areas**: Docker Compose networking, Ansible deployment, Home Assistant, Home Connect, NordVPN integration, selective outbound routing.
- **Expected output / behaviour**: A written architecture recommendation with tradeoffs and a migration plan; no implementation in this phase.
- **Related existing functionality**: The repository has an OpenVPN container and a `network_mode: "service:openvpn"` pattern for VPN-dependent services, but this is considered too tightly coupled for the new design.

## Technical context

### Database

None. This is infrastructure and networking work.

### REST API

None planned. The design may affect container egress and proxy/network configuration but does not require application API changes.

### Integrations

- NordVPN subscription and its supported client/protocol options.
- Home Assistant's Home Connect integration, which currently reports an authentication/connectivity error requiring VPN access.
- Existing Docker Compose and Ansible deployment on the `chris` host.
- Existing OpenVPN profile and optional `chris-vpn` Compose profile as historical reference.

### Graphify / code exploration

Repository and Git-history exploration found:

- `home-server/docker-compose.yaml` historically routes Home Assistant and Jellyfin through `network_mode: "service:openvpn"`.
- `d123265` introduced the OpenVPN container.
- `49d81d8` isolated VPN-dependent services into a separate Compose profile because VPN/provider failures could block the whole stack.
- Current Ansible defaults and tasks keep the VPN profile optional and start it best-effort.
- The OpenVPN container uses `/dev/net`, `NET_ADMIN`, a read-only root filesystem with tmpfs, and a bind-mounted VPN configuration.
- A plain HTTP proxy would be less invasive for HTTP(S)-only Home Connect traffic, but it would not cover arbitrary protocols or future qBittorrent torrent traffic.
- Host policy routing could provide selective routing without shared container namespaces, but would add substantial operational complexity and host-level failure modes.
- No Home Connect configuration references were found in the three repositories; the current error is likely stored in Home Assistant runtime state or external integration configuration.

## Risks and complexity

| Area | Detail |
|------|--------|
| Edge cases | Home Assistant must retain local LAN discovery/control and stable inbound access while any selected outbound traffic uses NordVPN. DNS routing and VPN reconnect behaviour need explicit treatment. |
| Dependencies | NordVPN protocol/configuration choice, credentials handling, the Home Connect integration's actual network requirements, and the existing optional OpenVPN profile. |
| ADR / security review needed | No, per user direction. Security implications should still be covered in the recommendation, especially credentials, DNS leaks, fail-closed behaviour, and accidental VPN-wide routing. |
| Watch points | Minimize operational complexity; avoid tightly coupling application containers to a VPN container; preserve independently configurable ports and normal direct networking. |
